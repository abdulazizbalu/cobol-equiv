# cobol-equiv

[![CI](https://github.com/abdulazizbalu/cobol-equiv/actions/workflows/ci.yml/badge.svg)](https://github.com/abdulazizbalu/cobol-equiv/actions/workflows/ci.yml)

A reproducible harness for checking that a Python translation of a COBOL
program behaves exactly like the original, using GnuCOBOL as the oracle.

## What this is, and what it is not

There are many tools and agent pipelines that translate COBOL into Java,
Python or other languages, many of them LLM-based. This project is not one of
them. It does not translate anything.

It is:

1. **A Python runtime for COBOL data and arithmetic semantics**
   (`cobol_equiv.runtime`): PICTURE clauses, USAGE DISPLAY / COMP-3 / COMP /
   COMP-5 storage, MOVE, numeric editing, ROUNDED, ON SIZE ERROR,
   intermediate precision, STRING / UNSTRING / INSPECT. Every rule is
   compared byte for byte with GnuCOBOL on generated test programs, and the
   cases it does not model are refused with an error instead of guessed.
2. **A differential testing harness** (`cobol_equiv.harness`): compile the
   COBOL program with `cobc`, run it and a Python translation on the same
   inputs (fixed regression vectors plus Hypothesis-generated ones derived
   from the record layouts), compare stdout and output files byte for byte,
   and report the first difference by line and field name.
3. **Later (not in this repository yet):** a benchmark and failure taxonomy
   for LLM-produced translations. There are no LLM features here.

## Reproduce

Requires Linux, Python 3.10-3.12 and GnuCOBOL 3.1.2 (`apt install gnucobol3`
on Ubuntu 24.04).

```sh
python -m pip install -e ".[dev]" -r requirements-repro.txt
python -m cobol_equiv.reproduce     # regenerates everything in results/ (a few minutes)
python -m pytest                    # unit, oracle and corpus tests
```

`requirements-repro.txt` pins the Hypothesis version: the generated inputs,
and therefore which mutants are detected by generated inputs, depend on it.
CI checks that a fresh run reproduces the committed `results/` exactly.

## Checking your own translation

A translation is a Python module with

```python
def main(stdin: bytes, input_files: dict[str, bytes]) -> tuple[bytes, dict[str, bytes]]:
    ...  # return (stdout bytes, {output file name: content})
```

Describe the COBOL program in a `spec.py` (input record layouts, output
files, field layouts for readable reports, regression vectors; see
`corpus/*/spec.py` and [docs/harness.md](docs/harness.md)), then:

```sh
python -m cobol_equiv.harness.check corpus/loancalc my_translation.py --examples 200
```

The translation may use `cobol_equiv.runtime` or anything else.

## Supported COBOL subset

Data: PICTURE `9 S V X A Z * $ , . + - CR DB B 0 /` with repeat counts;
USAGE DISPLAY (trailing embedded sign), COMP-3, COMP/BINARY, COMP-5; groups,
fixed OCCURS, REDEFINES, VALUE.
Statements modelled by the runtime: MOVE (numeric, alphanumeric, group,
edited receivers), ADD, SUBTRACT, MULTIPLY, DIVIDE (with REMAINDER) and
COMPUTE with ROUNDED (default mode) and ON SIZE ERROR, STRING, UNSTRING,
INSPECT (TALLYING, REPLACING, CONVERTING), DISPLAY formatting, LINE
SEQUENTIAL and fixed-length sequential files. Control flow (IF, EVALUATE,
PERFORM) is written directly in Python by the translation.

Details, including every case the runtime refuses, are in
[docs/runtime.md](docs/runtime.md). The behaviours that most often break
translations are collected in [docs/semantic-traps.md](docs/semantic-traps.md).

## Known limits

- **The oracle is GnuCOBOL 3.1.2 with `-std=default`, and only that.** The
  results say nothing direct about IBM Enterprise COBOL or Micro Focus.
  IBM Enterprise COBOL differs in places that matter for translations: EBCDIC
  data and collating sequence, the sign convention of zoned decimal data,
  binary truncation (the TRUNC compiler option), intermediate precision
  (ARITH option and its own rules for intermediate results), and a number of
  edge cases. A translation that matches GnuCOBOL can still differ from the
  mainframe program it came from.
- No CICS, no DB2 or embedded SQL, no EBCDIC or VSAM file formats, no
  copybook processing, no indexed or relative files, no SORT, no CALL.
- The runtime refuses some cases instead of modelling them (listed with
  counts in `results/SUMMARY.md`), for example values of 2^63 and above
  stored into binary items, and GnuCOBOL's integer fast path for
  single-operand ADD/SUBTRACT.
- The oracle cases are generated from boundary values and seeded random
  values. Agreement on them is evidence, not proof.
- The corpus is small (10 programs), written by the author of this
  repository for this purpose. It is not production code and does not
  represent the size, style or history of real mainframe applications.
- The mutation results measure the harness on these programs and these
  mutants only. Which mutants count as "equivalent" is a manual judgement,
  written down for each one in `results/mutation.csv`.

## Repository layout

```
src/cobol_equiv/runtime/   COBOL data semantics in Python
src/cobol_equiv/oracle/    generated GnuCOBOL programs per runtime rule
src/cobol_equiv/harness/   compile, run, generate inputs, compare, mutation run
corpus/<program>/          program.cob, reference.py, spec.py, mutants.py
results/                   committed CSV files and the generated SUMMARY.md
docs/                      runtime subset, harness, semantic traps
```
