# Benchmark: LLM translations of COBOL to Python

The benchmark measures COBOL-to-Python translations produced by one large
language model with the differential harness of this repository. The
protocol, written and merged before any translation was generated, is
[docs/benchmark-protocol.md](benchmark-protocol.md); its last section lists
every deviation.

## What was measured

- **Translations.** LLM output. The model name, as passed to the client and
  as reported in every reply, is recorded in `benchmark/manifest.json`
  (`frozen_before_first_call.model_id`) and in each `call.json`; the date
  of each call is in `call.json` (`started_utc`). Every prompt, raw reply
  and extracted translation is committed under `benchmark/runs/`.
- **Programs.** Track E: programs from the Open Mainframe Project COBOL
  course and Rosetta Code (`benchmark/corpus-e/`, screening record in
  `screening.csv`). Track R: programs written for this repository
  (`corpus/`, `benchmark/corpus-r/`).
- **Conditions.** A: one call, with the `cobol_equiv.runtime` package and
  its API sheet. B: each A attempt plus up to 3 repair rounds with feedback
  from DEV vectors. C: one call, Python standard library only. Three
  attempts per program for A and C.
- **Score.** A translation passes when its standard output and output files
  are byte-identical to those of the program compiled with GnuCOBOL 3.1.2
  on every HELD-OUT input (generated and boundary inputs never shown to the
  translator). Passing translations are re-run against GnuCOBOL 3.2.

## Notes on the results

- Most crashes of condition A are `TypeError` from comparing two
  `CobDecimal` values with `<` or `>` (see "Crash messages" in the table
  block), and the time-outs of condition A are loops that end on
  `dec(x) == dec(y)`, which is never true because `CobDecimal` compares by
  identity. The API sheet shown to the translator says `dec` values can be
  used for comparisons (deviation D13). These failures come from the
  benchmark material as much as from the translations; the A vs C
  comparison is affected by it. The section on sensitivity below repeats
  the measurements with the runtime defect corrected (D14).
- In condition B, the repair rounds fixed the failing A attempts within
  the first round (see "B after round" in the table block).
- The failures of condition C are wrong outputs, not crashes. Their causes
  include values wider than an edited PICTURE (GnuCOBOL edits the
  truncated value with a leading zero), ACCEPT input longer than the
  receiver, a negative zero, DISPLAY formatting, conversion of non-numeric
  input text and a decimal-scale error (one line per attempt in
  benchmark/results/failures.csv).
- The 3.2 re-run results are in the table block; one program has no 3.2
  outputs (D10).

## Sensitivity to the CobDecimal comparison defect (D14)

The numbers above are the registered results and stay the primary ones.
`CobDecimal` in the runtime frozen for the benchmark (1.0.0) has no
comparison operators: `==` compares identity and `<` raises `TypeError`
(D13). Runtime 1.1.0 compares by value. The committed translations, not
changed, were verified again with the corrected runtime, within the scope
given in D14: translations that compare or hash CobDecimal values (static
scan), the B attempts derived from them, and a fixed sample of 30 other A
and B units; condition C does not use the runtime. The tables below are
generated by `python -m cobol_equiv.benchmark.analysis report` from
`verdicts.csv`, `verdicts-corrected.csv`, `failures.csv`,
`failures-corrected.csv`, `eq-sites.csv` and `comparisons-corrected.csv`.

What the correction changes (read with the tables above; the corrected
analysis was not pre-registered and does not replace the registered tests):

- **Condition A.** Every A attempt that failed because of the defect passes
  with the corrected runtime: the `TypeError` crashes and the time-outs
  (table of changed attempts). The registered A pass rates understate what
  the A translations do on a runtime that compares as COBOL does. Two A
  failures remain, with causes unrelated to the defect (a wrong output and
  a syntax error, `failures-corrected.csv`).
- **A vs B.** In the registered results B passes where A fails on several
  pairs (no pair the other way); with the correction, B and A differ on one
  pair per track. The registered advantage of the repair rounds is, almost
  entirely, the repair of the defect.
- **A vs C.** In the registered results the McNemar tests show no
  difference. With the correction, A passes on more pairs than C on both
  tracks; on track R the McNemar p value is below 0.05 after the Holm
  correction (within the corrected family of four tests), on track E it
  does not. The sign test over programs, which does not assume that the
  attempts of a program are independent, is not significant on either
  track.

What it does not change:

- Condition C verdicts (C does not use the runtime), the C failure
  categories, pass@3 of every condition, and the B results (every final B
  attempt passes in both analyses).
- The GnuCOBOL 3.2 re-run: every final translation that passes on 3.1.2
  and has 3.2 outputs also passes on 3.2 (one program has none, D10).
- No reference translation, oracle test or harness path uses CobDecimal
  comparisons: every reference passes all its vectors with both runtimes and
  makes no comparison or hash call (`refcheck` fails otherwise), and the test suite runs
  with a trap that fails on any such call outside the comparison tests
  (`tests/conftest.py`, CI).

## Reproducing

Generating translations is not reproducible: the model is sampled with the
client's default settings and is not available offline. Verifying them is:

    python -m cobol_equiv.benchmark.fetch            # Track E sources
    python -m cobol_equiv.benchmark.verify --check   # every translation, registered runtime (1.0.0)
    python -m cobol_equiv.benchmark.ci check --runtime corrected   # D14 scope, corrected runtime (1.1.0)
    python -m cobol_equiv.benchmark.analysis report --check
    python -m cobol_equiv.benchmark.audit            # artifacts vs manifest

CI runs the last two on every pull request and the verification split as
described below.

### Verification in CI

A full verification of one runtime mode (D14) takes hours on a GitHub
runner, so CI does not run it on every pull request.

- **Scope of the corrected mode (D14).** Only the units in the D14 scope are
  run with the corrected runtime: the condition A and B translations in
  which the static scan (`eqscan`, `benchmark/results/eq-sites.csv`) finds a
  CobDecimal compared with `==`, `!=`, `<`, `<=`, `>`, `>=` or `in`, or
  hashed, every condition B attempt derived from such an A translation, and
  a fixed sample of 30 other A and B units (seed `crc32("d14-sample")`).
  Condition C translations do not import the runtime (checked: none
  mentions the package, and they run with `python -I -S`), so they are not
  run again. Outside the scope, `verdicts-corrected.csv` holds the
  registered rows, and CI checks that they are identical copies.
  `python -m cobol_equiv.benchmark.ci sensitivity` runs the scope in both
  modes and writes `verdicts-corrected.csv`, `comparisons.csv`,
  `comparisons-corrected.csv` (scope units only) and `verify-inputs.json`.
- `benchmark/results/verify-inputs.json` holds, for each runtime mode and
  unit (track, program, condition, attempt), the SHA-256 of the unit's
  translation files, its vectors file, the program's spec, the verification
  code, the runtime mode and, for conditions A and B, the runtime version,
  and the SHA-256 of the runtime's source. A change of the verification
  code therefore marks every unit as changed. CI
  fails when the file is not current, and when the runtime's source changed
  under the same version number.
- On pull requests and pushes to main, the `verify` jobs of `ci.yml` (one
  per runtime mode and track) re-verify the units whose input hash or
  committed rows differ from those of the base branch (in the corrected
  mode, within the D14 scope), plus a fixed sample of the other units: 2
  per (track, condition), seed `crc32("ci-sample")`. Their rows must equal
  the committed ones, apart from the machine-dependent counts.
- Finished units are cached with `actions/cache`. The cache key is the hash
  of `verify-inputs.json`, of the benchmark and runtime code and of the
  programs' `spec.py` files; each saved unit also carries verify's own key
  (content of the translation files, vectors, spec, runtime and
  verification code), so a unit is taken from the
  cache only if none of these changed. The sample units are always run
  again with an empty cache.
- `benchmark-full.yml`, started by hand and every Monday, runs every unit
  of the registered mode and the D14 scope of the corrected mode, in four
  parallel jobs (mode x track), with an empty cache. In the registered
  mode it also fails if a unit outside the D14 scope makes any CobDecimal
  comparison or hash call, which checks the static scan on every unit.
- Units run in parallel on the number of CPU cores minus one.

Locally, `python -m cobol_equiv.benchmark.verify --check` verifies the
registered mode in full, and `python -m cobol_equiv.benchmark.ci check
--runtime corrected` the corrected mode within the D14 scope.

## Limits

- One model, one client version, one date, default sampling. The results
  say nothing about other models or settings.
- The corpus is small (see the tables for the counts). Track E programs
  and their task statements are public and may be in the model's training
  data. Track R programs were written for this repository together with
  the harness and exercise what the harness checks.
- GnuCOBOL is the only oracle; no IBM compiler was used. Behaviour that
  differs between compilers is not covered, beyond the 3.2 re-run.
- HELD-OUT inputs come from generators derived from record layouts and from
  boundary values of the PICTUREs. A translation that passes them can still
  differ from the program on other inputs. Several programs have small
  input domains (for example `rc-decision-tables`, whose HELD-OUT set holds
  only boundary inputs).
- Condition B uses DEV feedback, which shows inputs and expected outputs of
  the COBOL program; it measures repair with test feedback, not translation
  alone.
- Failure categories other than the automatic ones were assigned by hand
  by a single rater, with no second rating. The classification list hid
  the condition, attempt and file path, but the blinding was partial: a
  translation's code shows whether it uses the runtime, so condition C
  translations are recognisable.
- The API sheet of conditions A and B contains an error, and the runtime
  a defect behind it (D13, D14). The corrected numbers are a sensitivity
  analysis that was not pre-registered.
- Per-vector time limits are wall-clock; a translation close to the limit
  can pass on one machine and time out on another.
